# 18 - Support desk

Status: integrated (foundation T0 + slices T1–T8 + integration pass, task I, 2026-09-08 — §17). Every slice documents its rules in its own section; §17 lists the wiring between them, the seeds, the operator setup (Resend inbound, Fly worker secrets) and the gates that ran.

## 1. Purpose and product rules

`/ops/support` is the ticket desk of Track's own operators inside the Track Operations console (docs/17): everything a customer or prospect sends by e-mail, through the public contact form or from the customer dashboard becomes a ticket with a number, a requester, a workflow state, an SLA clock and a conversation. `/app/support` is the customer-facing counterpart: an organisation's members see their own tickets and reply from the dashboard.

Binding rules (in addition to docs/17 §1):

- **Every mutation is a server action** with `requirePlatform(role, permission)` (console) or `requireOrgContext(permission)` (customer dashboard), zod validation and an audit entry (`auditPlatform` / `recordAudit`). Audit diffs carry ids and field changes — never message bodies, e-mail contents or attachment bytes.
- **Customers never see** internal notes, agent-only fields (assignee, SLA policy, breach flags, pause state, tags), other organisations' tickets, or platform users' details beyond the agent's display name. The database enforces the first three (RLS, §3); the loaders enforce the rest (`SUPPORT_TICKET_CUSTOMER_COLUMNS`).
- **Inbound e-mail is untrusted input.** HTML is sanitised server-side to an allow-list before it is stored (`sanitizeHtml`), scripts / styles / forms / remote images are stripped, and the console never renders provider HTML unsanitised. Attachments: at most 5 per message, 5 MB each, allow-listed content types, stored in the database with organisation scoping; the virus-scan hook is a documented placeholder (§5).
- **No invented metrics.** SLA states and report figures come from real timestamps (`first_responded_at`, `resolved_at`, message times) or are shown as "not measured".
- **UI**: WCAG 2.2 AA, keyboard operable, 44 × 44 targets, no nested interactive elements, tables with mobile stacking, six-locale strings (shared vocabulary in namespace `support`, module copy in the slices' own namespaces).

### SLA semantics (for the slices)

- `first_response_due_at` / `resolution_due_at` are computed from `created_at` (or the reopening time) with the policy's business hours; `first_responded_at` is the first outbound agent message, `resolved_at` the transition to `solved`.
- `pending` pauses the clock: `paused_at` is set on entering, `pause_total_ms` accumulates on leaving; due times shift by the accumulated pause.
- `breached_first_response` / `breached_resolution` flip when the clock passes the due time (worker job, `sla_breach` event; `sla_warning` at `warning_percent`). A ticket without a policy has no due times and shows "no SLA policy" — never a guessed figure.

## 4. E-mail flow

### Outbound (`apps/web/src/server/support/mail.ts`)

`sendTicketMail({ ticket, message, locale, settings })` → `buildTicketMail` (pure, tested) → `sendMail` (`apps/web/src/server/mail.ts`: SMTP → Resend → local outbox `.local/mail`). The transport accepts `from`, `cc`, `headers`, `messageId`, `inReplyTo`, `references` and `attachments` since T0; older callers are unchanged.

| Header       | Value                                                                                                       |
| ------------ | ----------------------------------------------------------------------------------------------------------- |
| From         | `"<from_name>" <from_address>` (settings row; `SUPPORT_FROM_ADDRESS` overrides)                             |
| Reply-To     | `support+t<number>@<inbound_domain>` — the primary routing key of every answer                              |
| Subject      | `Re: [Track #<number>] <subject>` (one tag, one reply prefix)                                               |
| Message-ID   | `<t<number>.<ulid>@<inbound_domain>>` — stored on `support_messages.message_id` **before** sending          |
| In-Reply-To / References | the customer's last message id and the thread so far                                            |
| X-Track-Ticket | the number (diagnostics)                                                                                  |
| Auto-Submitted / X-Auto-Response-Suppress | `auto-replied` / `All` on automated messages (`kind: "auto"`) only                 |

Bodies: text + HTML (agent HTML is already sanitised; plain text is rendered through `textToHtml`), the agent's display name and the desk signature (agent messages only), and a transactional footer in the recipient's locale ("this e-mail belongs to ticket #…, reply to continue") — no unsubscribe link (correspondence the person asked for). A transport failure never throws: the caller records `delivery_status = failed` / `delivery_error` on the message and shows it.

### Inbound (task T3: `apps/web/src/server/support/inbound.ts` pure helpers, `inbound-handler.ts` pipeline + Drizzle store, route `POST /api/support/inbound`)

The route verifies, parses and hands over; `handleInboundEvent(email, deps)` does the work against the `InboundStore` contract (unit-tested with an in-memory store; `createDrizzleInboundStore` is production, covered by the integration test). The handler runs as **`tracksite_worker`** (`withWorker`, BYPASSRLS): a webhook has neither an operator nor a tenant session — it is system processing like the worker jobs, not an operator action, so `withPlatform` / `auditPlatform` do not apply — and every row it writes carries the organisation id the tenant policies scope on. No message body ever reaches an event payload, the ledger, a log line or a webhook answer.

1. **Verify** the Resend webhook (`verifySvixSignature`): headers `svix-id`, `svix-timestamp`, `svix-signature`; HMAC-SHA256 over `${id}.${timestamp}.${rawBody}` with the base64 secret after `whsec_` (`RESEND_WEBHOOK_SECRET`), base64 signature, any `v1,…` entry may match, ± 5 minutes, constant-time comparison. The raw body is read once (≤ 1 MB, else 413) and nothing is parsed before the signature is good; without a secret the route answers 503, with a bad one 400.
2. **Idempotency** (`support_inbound_events`, `provider_event_id = svix-id`, unique): the row is inserted `received` (`ON CONFLICT DO NOTHING`); an existing row that is `processed` / `ignored` → 200 `duplicate`; still `received` and younger than `INBOUND_EVENT_STALE_MS` (10 min) → 409 `IN_PROGRESS` (another instance is on it; Resend retries later); `failed` or stale → reprocessed (`retry`). A retry never stores a mail twice: before fetching or routing, the handler looks the mail's own `email_id` up in `support_messages.provider_message_id` (inbound rows, `findInboundMessage`); a hit — the earlier attempt committed the ticket or message and failed afterwards (acknowledgement, delivery update, ledger, connection) — is answered with the stored rows (`route: "stored"`, `created: false`, the stored ticket and message ids, no new acknowledgement) and the ledger row ends `processed`. Two *concurrent* deliveries of one mail (different `svix-id`s — a re-sent webhook racing a retry — both pass the lookup before either commits) are serialised inside the store: `createTicket` / `appendMessage` take a transaction-scoped advisory lock on the mail's `email_id` (`pg_advisory_xact_lock(hashtextextended(…))`) and re-check for the winner's row; the loser rolls back with `InboundAlreadyStoredError` and is answered with the stored rows as well (integration-tested with two parallel transactions). A partial unique index on `support_messages(provider_message_id) WHERE direction = 'inbound'` would make the guarantee structural (§9). Delivery events posted to this URL take the same ledger (§"Delivery events"); every other event type is acknowledged with 200 and ignored.
3. **Fetch**: `email.received` carries ids, addresses, subject and attachment names only (`parseResendReceivedEvent`) — no bodies, no headers, no sizes. `createResendReceivingClient` (`RESEND_API_KEY`, `fetch`, 15 s timeout) reads `GET /emails/receiving/{email_id}` — the endpoint behind the SDK's `resend.emails.receiving.get` — and `mergeReceivedEmail` fills bodies, the full header set (also In-Reply-To / References when the event had none), cc, subject and attachment sizes; values the event already carried win. Resend returns inline images as `data:` URIs inside `html` (its default `html_format`), which the sanitiser keeps. Without the key the ledger row fails with "receiving api not configured" and the route answers 500, so Resend retries once the key exists.
4. **Loop guard** (`detectAutoReply`, `isOwnAddress`): `Auto-Submitted` ≠ `no`, `Precedence: bulk|junk|auto_reply|list`, `X-Autoreply` & co., list headers, delivery-status reports, out-of-office subjects in the six languages → the mail is stored but never answered automatically (`autoReply` + reason in the event); mails from the desk's own sender or reply domain are dropped (ledger `ignored`, reason `own_address`). `X-Auto-Response-Suppress` alone keeps the mail human but suppresses the acknowledgement.
5. **Spam** (`spamVerdict`, conservative): DMARC `fail`, SPF **and** DKIM `fail` (read from the receiving MTA's `Authentication-Results` only — the trusted instance of step 6; `ARC-Authentication-Results` is never read; `Received-SPF` carries no authserv-id and is ignored), an upstream `X-Spam-Flag: YES` / `X-Spam-Status: Yes`, or a blocked sender (§"Blocked senders") → a new ticket is created with status `spam` (no SLA policy, no due times, no acknowledgement) so an operator can rescue it; a spam-flagged reply to an existing ticket is appended without reopening. SPF alone failing is not spam — forwarders break it every day. The verdict and the authentication results land in the event payload.
6. **Route** (`routeInbound`) with a **guard**: plus address `support+t<number>@<inbound_domain>` → `In-Reply-To` / `References` against `support_messages.message_id` / `provider_message_id` → subject tag `[Track #<number>]` → otherwise new. A plus-address or subject match is accepted only from the ticket's requester and the conversation's participants (from / to / cc of the stored non-note messages) **and** only when the `From` address is backed by an authenticated identity (`senderAuthentication`, `replyGuard`): ticket numbers are sequential and `From` is forgeable for any domain without a DMARC policy (the verdict is then `dmarc=none`, which the spam rule does not catch), so the address alone would let anyone drop a message into a victim's ticket — visible to that organisation in `/app/support`. "Authenticated" means, from the receiving MTA's `Authentication-Results`: `dmarc=pass` (a `header.from` it names must align with `From`), or `dkim=pass` whose `header.d` / `header.i` aligns with the From domain, or `spf=pass` whose `smtp.mailfrom` aligns (relaxed alignment: equal or parent / child domain). A pass on a foreign domain or a bare pass proves nothing about `From` and does not count; without the header the mail is unauthenticated. **Which header is believed** (`trustedAuthenticationResults`, RFC 8601): a mail may carry any number of `Authentication-Results` headers — a forwarder's, or one the sender typed in (`Authentication-Results: x; dmarc=pass header.from=<victim>` costs nothing), and Resend's receiving API collapses repeated headers into one string. The desk therefore reads exactly one instance — the **first** (the receiving MTA prepends its trace headers, so its verdict comes first; the scan stops at the first unquoted comma outside comments or at a segment that is no `method=result` clause, i.e. where a collapsed second instance begins) — and only when its authserv-id is one of `SUPPORT_AUTHSERV_ID` (§5 step 3). Nothing configured, a foreign id first, an instance without an authserv-id, or no header at all → no results: the mail counts as unauthenticated and the spam rule of step 5 sees nothing (fail closed). RFC 8601 §5 obliges the MTA to strip incoming headers claiming its own authserv-id, which is what makes the pinned instance a verdict about *this* delivery — §5 step 3 says how to verify that once. `ARC-Authentication-Results` is **never read**, not even as a fallback when `Authentication-Results` is missing or foreign: that stripping covers `Authentication-Results` only, while ARC sets are preserved by every hop by design (RFC 8617 §5.1), so a sender who knows the configured id (anyone with a Resend Inbound account sees it) could ship `ARC-Authentication-Results: i=1; <id>; dmarc=pass header.from=<victim>` and it would arrive intact — and an AAR is a sealer's verdict about an earlier hop, never the receiving MTA's about this delivery. A mail that carries only ARC headers is unauthenticated like one without any. Every `created` / `reply` payload records the id seen and whether it was trusted (`authservId`, `authservTrusted`); an untrusted id also logs `support.inbound.authserv_untrusted`. Anyone else's mail — a stranger, or the requester's address without aligned authentication (a forger, but also a mailing-list relay that broke DKIM and SPF) — opens a **new** ticket whose `created` event carries `intendedTicketNumber` and `replyGuard` (`stranger` / `unauthenticated`); the agent merges it when it is genuine. A thread match carries the direction of the row it hit (`findTicketByMessageIds` → `matched`): the desk's **own** Message-IDs (outbound rows, `t<number>.<ulid>@…`) are unguessable, so a match on one is accepted from any sender regardless of authentication (a cc'd colleague replying, a forwarded mail); a **customer-supplied** Message-ID (an inbound row — an id that sits in every mailbox and list archive the mail reached) proves nothing and is guarded exactly like a plus-address match (requester or participant, authenticated). Because a reply to a desk mail carries the plus address (its Reply-To) *and* the thread ids, a refused plus-address / subject match falls back to the thread ids before a new ticket is opened — a customer-supplied id is guarded again there and cannot rescue it. A `dmarc=fail` in the trusted instance outranks every pass. When several stored rows carry one of the ids, the desk's own outbound rows win, then the oldest row. Every `created` / `reply` payload records `senderAuthenticated` and `senderAuthenticatedVia` (`dmarc` / `dkim` / `spf` / null). A reply to a merged ticket lands on the merge target (one hop); the merged-away ticket's requester and correspondents stay entitled to reply through its own plus address and subject tag (`getTicket` unions both tickets' participants).
7. **Append** (`appendMessage`, one transaction): the message (sanitised `html_body`, `text_body` from `text` or `htmlToText`), attachments, `last_customer_message_at`, a `reply` event. `solved` / `closed` → `open` and `pending` → `open` are the SLA engine's `statusTransition` with the ticket's own policy (`getSlaPolicy`, §10): a reopen counts `reopen_count + 1`, clears `resolved_at` / `closed_at` and restarts the resolution clock — and the first-response clock while unanswered — from now (`reopened` event), so the worker never flags the stale due time a minute later; leaving `pending` closes the pause (`pause_total_ms += now − paused_at`, `paused_at = null`) and shifts the running due times by its **business minutes** (`status` event with `reason: customer_reply`); `new`, `open`, `on_hold` (waiting on a third party — the agent decides) and `spam` keep their status. Replies are never acknowledged.
8. **Create** (`createTicket`, one transaction): requester e-mail → `user` (case-insensitive) → memberships: exactly one → `organization_id` and `requester_user_id`; several or none → `organization_id = null` (`membershipCount` in the event; the console links the organisation later). The link is applied **only when the `From` is authenticated** (step 6's `senderAuthentication`): a forged From of a known member — trivial for a domain without DMARC — must not open a ticket that member's whole organisation sees in `/app/support` under that member's name. Unauthenticated, both fields stay null, the `created` payload carries `requesterLinkWithheld: true` (and `organizationMatched: false`), the SLA policy is the default one, and an agent links the ticket after review; the requester's stored locale is still used for the ticket language (harmless). Locale (`detectInboundLocale`, source recorded as `localeSource`): the user's stored locale → `Content-Language` / `Accept-Language` / `X-Accept-Language` → a text heuristic over six stop-word lists (a language wins only with ≥ 3 distinct hits and a margin of 2, otherwise no guess) → English. SLA: the policy whose `plan_ids` contains the organisation's `subscriptions.plan_id`, else the default policy; `first_response_due_at` / `resolution_due_at` = `received_at` + the priority's business minutes inside the policy's windows and time zone (the engine's `computeDueDates`, §10 — DST-safe; no windows = wall-clock minutes; a missing target stays null — never a guess). Priority `normal`, channel `email`, status `new` (or `spam`).
9. **Attachments**: `screenAttachments` (≤ 5, ≤ 5 MiB, allow-list) → bytes via `GET /emails/receiving/{email_id}/attachments/{id}` → signed `download_url` (https only, the limit is enforced on `Content-Length` and again on the buffered bytes) → `sha256` → `AttachmentScanner` (`noopAttachmentScanner` until a scanner exists) → `support_attachments` with the ticket's organisation id. Refused files — `type_not_allowed`, `too_large`, `size_unknown`, `too_many`, `download_failed`, `scanner_rejected` — are listed in an internal **system note** (`direction = note`, agent-only, "2 attachments refused: …") and in the event payload: names and reasons, never contents. Sanitised HTML above `HTML_BODY_MAX_CHARS` (1 MB) loses its inline `data:` images; above that again `html_body` is null and the text body stands alone.
10. **Acknowledgement** (new, non-spam tickets only): requires `support_settings.auto_reply_enabled` (seeded `false` — switch it on in Support → Settings once DNS exists), no auto-reply verdict, no `X-Auto-Response-Suppress`, a sender without the `do-not-email` flag, a From that is either unknown or authenticated (a known member's address without aligned authentication gets none — never mail a possibly impersonated member about a ticket they did not open), and fewer than `ACK_MAX_PER_SENDER` (3) acknowledgements already sent to that address within `ACK_WINDOW_MS` (24 h, `countRecentAcknowledgements` over outbound `author_kind = system` rows): an auto-responder that strips every loop header and answers each acknowledgement with a fresh mail gets at most three ticket + acknowledgement rounds a day, then runs dry. The first reason that applies is recorded as `ackSkipped` (`spam` / `disabled` / `auto_reply` / `suppressed` / `do_not_email` / `unauthenticated` / `rate_limited`, `acknowledgementSkipReason`) in the `created` payload and the outcome (null when the acknowledgement was attempted); a rate-limited skip also logs `support.inbound.acknowledgement_rate_limited`. The outbound row (`author_kind = system`, `delivery_status = queued`, Message-ID `t<number>.<ulid>@<inbound_domain>`, In-Reply-To / References on the customer's mail, `reply` event with `auto: true`) is stored **before** `sendTicketMail`; afterwards it becomes `sent` + `provider_message_id` (Resend's id, which the delivery webhooks match) or `failed` + `delivery_error`. Copy: `acknowledgementText` × 6 (greeting by name or generic, the ticket number, "reply to this e-mail"), sent with `kind: "auto"` (`Auto-Submitted: auto-replied`, `X-Auto-Response-Suppress: All`). An acknowledgement never counts as the first response. The whole block runs after the ticket's commit and is fenced: a failure inside it (the outbound insert, the transport, the delivery update) is recorded as `ackError` in the outcome and a warning log line, never thrown — a thrown error would fail the event and make Resend retry a mail that is already stored. `acknowledged` is true as soon as the transport accepted the mail, even if the delivery update was lost afterwards (`ackError` then names that error).
11. **Timeline and ledger**: `created` / `reply` (+ `reopened` / `status`) with actor `customer`; payloads carry channel, locale + source, organisation matched (and `requesterLinkWithheld`), SLA policy id, spam / auto-reply verdicts, authentication results with the authserv-id seen and its trust (`authservId`, `authservTrusted`), `ackSkipped`, attachment counts and refusals, `messageId` (the row id). The ledger row ends `processed` with the ticket id, `ignored`, or `failed` with the error (shown on the Support → Settings overview as the inbound e-mail ledger, §11).

### Delivery events (`apps/web/src/server/support/delivery.ts`; routes `POST /api/support/delivery` and `/api/support/inbound`)

| Event                    | `delivery_status`                                       |
| ------------------------ | ------------------------------------------------------- |
| `email.sent`             | `sent`                                                  |
| `email.delivered`        | `delivered` (`delivery_error` cleared)                  |
| `email.delivery_delayed` | unchanged (still in flight)                             |
| `email.bounced`          | `bounced`, `delivery_error = "<type>/<subType>: <message>"` |
| `email.complained`       | `complained` + do-not-email flag (below)                |
| `email.failed`, `email.suppressed` | `failed`, `delivery_error = reason`           |

Matching by `data.email_id = support_messages.provider_message_id` on outbound rows; `nextDeliveryStatus` moves forward only (`sent` after `delivered` is ignored; `bounced` / `complained` / `failed` are terminal), so out-of-order deliveries are harmless. Events of mails that are no ticket mail (password resets, invitations) are acknowledged and recorded as `ignored`; the ledger and the answers (200 / 409 / 500) are those of the inbound route. **Complaint → do-not-email**: every ticket of the requester receives the tag `do-not-email` (`tags` event, actor `system`, `reason: complaint`) and one `audit_log` row `support.requester.do_not_email` (actor `{ kind: "system", name: "resend-webhook" }`, the ticket's organisation id, ids and the tag only). The inbound handler then never acknowledges that sender again and the console shows the tag; an agent lifts it by removing the tag.

### Blocked senders and do-not-email (no settings column in 0015)

Migration 0015 has no blocked-senders list, so the desk derives both flags from decisions already recorded (`senderFlags`, one query on `support_tickets.requester_email`): **blocked** = an agent moved a ticket of the sender to `spam` and it still is (a `status` event by an agent with `to: spam` on a ticket in status `spam`: marking a ticket as spam is the block, reopening it lifts it; further mails become `spam` tickets, never answered). A spam ticket the handler filed on its own verdict (step 5) does **not** block the address: `X-Spam-Flag` and, for a domain without DMARC, the `From` are the sender's to forge, so one forged mail could otherwise silence any customer address; **do-not-email** = a ticket of the sender carries the `do-not-email` tag (a complaint sets it, an agent may set or remove it). A dedicated `support_settings.blocked_senders` column with domain patterns is a follow-up (§9).

## 5. DNS and Resend setup

Outbound (sender domain `track.site`, already used for transactional mail): SPF (`v=spf1 include:amazonses.com ~all` or the record Resend shows for the domain), DKIM (the three CNAMEs from the Resend domain page), DMARC (`_dmarc.track.site` `v=DMARC1; p=quarantine; rua=mailto:…`). Verify the domain in Resend → Domains; `SUPPORT_FROM_ADDRESS` must be on a verified domain.

Inbound (reply domain, default `support.track.site`):

1. Resend → Domains → add `support.track.site` with **receiving** enabled; add the MX record Resend shows (`support.track.site MX 10 inbound-smtp.<region>.resend.com`-style value from the dashboard — copy it, do not guess) plus SPF/DKIM if the same domain also sends.
2. Resend → Webhooks → **Add webhook** with the endpoint `https://www.track.site/api/support/inbound` and the events `email.received`, `email.sent`, `email.delivered`, `email.delivery_delayed`, `email.bounced`, `email.complained`, `email.failed`, `email.suppressed` — one webhook, one signing secret → `RESEND_WEBHOOK_SECRET` (`whsec_…`, shown once after creation). The inbound route handles the delivery events itself. Optional split setup: a second webhook with the seven delivery events only → `https://www.track.site/api/support/delivery`, its secret in `RESEND_DELIVERY_WEBHOOK_SECRET`. `RESEND_API_KEY` must belong to the same Resend team: the route fetches bodies and attachment bytes with it (`GET /emails/receiving/…`), and the delivery webhooks match the `email_id` the same key returned when the ticket mail was sent.
3. Name the receiving MTA's authserv-id (`SUPPORT_AUTHSERV_ID`): send one mail to `support@support.track.site`, open the ticket it made and read `authservId` off its `created` event (the same value is in the log line `support.inbound.authserv_untrusted` that every inbound mail writes until the id is configured), then set `SUPPORT_AUTHSERV_ID=<that id>` (comma-separated when the MX writes several) and redeploy. Neither Resend's docs nor the SDK disclose the id, so it is never guessed: until it is set, every inbound mail counts as unauthenticated — plus-address and subject replies are refused (replies to desk mails still thread on the desk's own Message-IDs), known members are not linked to their organisation and get no acknowledgement, and the DMARC spam rule is off (§4 steps 5, 6, 8, 10). Verify the trust once, because it rests on Resend stripping foreign headers that claim its id (RFC 8601 §5): send a mail from an address whose domain has no DKIM / SPF alignment with the sender (a throwaway mailbox on another domain) that carries **both** a hand-written `Authentication-Results: <id>; dmarc=pass header.from=<that domain>` header and a hand-written `ARC-Authentication-Results: i=1; <id>; dmarc=pass header.from=<that domain>` header — its ticket's `created` payload must say `senderAuthenticated: false` (and `authservId: <id>` with `authservTrusted: true`, i.e. Resend's own verdict came first and the forged instance was stripped or sits behind it). If it says `true`, a forged header got through: unset `SUPPORT_AUTHSERV_ID` again (fail closed) and report it. The ARC header is part of the test even though the desk never reads ARC (§4 step 6): ARC sets are not stripped by anyone (RFC 8617 §5.1), so the check proves the whole pipeline end to end rather than one parser — a `true` there could only come from the desk reading ARC again.
4. Set `SUPPORT_INBOUND_DOMAIN=support.track.site` (or edit the settings row in Support → Settings); every ticket mail now carries `Reply-To: support+t<number>@support.track.site`. Switch `auto_reply_enabled` on in Support → Settings when the acknowledgement mail should go out (it stays off until then; acknowledgements are capped at three per sender and day, §4 step 10).
5. Optional catch-all: point `support@track.site` (the public address) to a Resend inbound address or forward it to the reply domain so mails without a ticket also arrive.
6. Test: send a mail to `support@support.track.site` → the ledger (`support_inbound_events`, shown on the Support → Settings overview, §11) shows the event as `processed` with the new ticket; reply to a ticket mail from a mailbox → the answer lands on the ticket (via `plus_address` in the `reply` event); Resend → Webhooks → the webhook's log shows the `200` answers (`{ ok, ticketId, number, created, … }` — ids and counts only).

Local development: no DNS — ticket mails land in `.local/mail/*.json` (attachments summarised, never their bytes). The webhook is exercised with `signSvix` in tests, with a `curl` whose `svix-*` headers are computed the same way, or — for browser-level tests — through `POST /api/support/dev-fixture` (§4 "Development fixture"), which needs no secret and no Resend account.

## 10. SLA engine (task T4: `apps/web/src/server/support/sla.ts`, worker `apps/worker/src/jobs/support-sla.ts`, editor `/ops/support/settings/sla`)

- **Engine** (pure, no database): business-hour arithmetic on the policy's `business_hours` (`{ timezone, days: { mon: [[540, 1080]] } }`, several windows per day merged, no window = 24 × 7, unknown zone → `Europe/Berlin`, DST-safe through `Intl`): `addBusinessMinutes`, `subtractBusinessMinutes`, `businessMinutesBetween`, `isBusinessTime`. `computeDueDates(policy, priority, from, pauses)` counts business minutes outside the pauses; a missing target gives `null`, never a guess. Lifecycle patches for `support_tickets`: `applyPolicyOnCreate`, `applyPolicyOnPriorityChange` (running clocks move by the target delta), `pauseClock` / `resumeClock` (due dates shift by the **business** minutes of the pause, `pause_total_ms` accumulates wall clock, a breach at pause time stays), `transitionStatus` (`pending` pauses, leaving it resumes, `solved` / `closed` stop the resolution clock, reopening restarts it from now, `spam` stops without resolution), `markFirstResponse`, `slaClockState` (none | paused | running | due_soon | breached | met from real timestamps only). `selectSlaPolicy`: plan match, then default, else no SLA.
- **Escalation JSON** (`support_sla_policies.escalation`): `warning_percent` (default 80), `notify_user_ids` (platform operators only), `escalate_to_admins` (default true), `auto_close_days` (absent → 7, `null` → never).
- **Worker job** `support-sla` (`JOB_SCHEDULE`, every minute, heartbeat + `WORKER_JOB_INTERVALS_MS`): for tickets with a running clock (`new` / `open` / `pending` / `on_hold`, not paused, not merged) it writes one `sla_warning` event per clock when the remaining business minutes reach the warning share (assignee e-mailed, nobody for an unassigned ticket), flips `breached_*` with an `sla_breach` event (assignee, named recipients and — when enabled — every `PLATFORM_ADMIN` e-mailed, six-locale plain text, ticket number and subject only), and auto-closes `solved` tickets after the policy's (or the default policy's) `auto_close_days` with a system `status` event. Findings are written under `FOR UPDATE` after re-reading the row, so several workers never double-flag; event payloads carry ids and field values only.
- **Editor** (`platform.sla.manage`, admin + two-factor): targets per priority in minutes / hours / days (5 minutes … 90 days, first response ≤ resolution), time zone (IANA), one window per weekday, escalation. Server actions (`saveSlaPolicyAction`, `setDefaultSlaPolicyAction`, `deleteSlaPolicyAction`) validate with zod + `parseSlaPolicyInput`, run as `tracksite_ops` and audit the changed settings (`support_sla_policy`); one policy per plan, exactly one default (never switched off, only replaced), deleting needs no referencing ticket. Strings: namespace `support-sla` × 6.
- Tests: `sla.test.ts` (web) and `support-sla.test.ts` (worker) share fixtures (Mon–Fri 09:00–18:00 Europe/Berlin, September 2026, the DST end in October) so the mirrored arithmetic stays in step.

## 11. Macros and desk settings (task T5: `apps/web/src/server/support/macros.ts` + `settings.ts`, actions `server/ops/actions/support-macros.ts` + `support-settings.ts`, pages `/ops/support/macros`, `/ops/support/settings`, `/ops/support/settings/general`; namespace `support-macros` × 6)

### Macros (`/ops/support/macros`, `platform.macros.manage`)

- **Scope rules** (`canUseMacro`, `canManageMacro`, `canCreateScope`): a `global` macro (`owner_user_id` null) is usable by every operator and created, edited and deleted by `PLATFORM_ADMIN` only — a support agent sees it read-only and creating one as global is refused (`scope_forbidden`). A `personal` macro belongs to one operator; nobody else sees it, not even an admin (another operator's personal macro answers `not_found`). Loaders run as `tracksite_ops`; the table has no tenant policy (customers never see macros).
- **Fields**: name ≤ 120, optional category ≤ 40 (existing categories are suggested), plain-text body ≤ 8 000, `actions` JSON `{ status?, priority?, tags_add?, tags_remove?, assign_to_self? }` (tags lower-case `[a-z0-9._-]`, at most 10 per list, a tag never in both lists), `usage_count`.
- **Placeholders** (`MACRO_PLACEHOLDERS`, `components/ops/support/macros/constants.ts` — pure, shared by the client editor, the server module and the tests): `{requester_name}`, `{requester_email}`, `{ticket_number}`, `{ticket_subject}`, `{agent_name}`, `{organization_name}`. `renderMacroTemplate` replaces known tokens (a missing value — unknown requester name, no organisation — renders empty, never a guess) and leaves unknown tokens as written so a typo is visible; the editor lists them (`unknownPlaceholders`) and previews the body with sample values.
- **List**: search (`/` focuses, Escape clears), scope and category filters, the actions of each macro, usage counts, `Edit` / `View` per row depending on `canManageMacro`.
- **`applyMacro` contract for the ticket detail slice** (`applyMacro(ticket: MacroTicket, macro: MacroDefinition, agent: MacroAgent): AppliedMacro`, pure, no writes): `text` is the body rendered for that ticket — a draft for the reply editor, never sent unseen; `changes` lists only the ticket fields the actions change (`status`, `priority`, `tags` — removed first, added second —, `assigneeUserId` for `assign_to_self`), `actions` the normalised stored actions, `values` the substituted placeholders. The detail slice checks the status transition against the ticket workflow, writes the message and the changes in its own transaction with the matching events, then calls `recordMacroUsage(tx, macroId)` (`usage_count + 1`). `loadMacroForUse(tx, macroId, agent)` applies the scope check; `listMacroOptions(tx, agent)` feeds the picker; `macroValuesFor(ticket, agent)` builds the placeholder values (`ticket.organizationName` when the requester's organisation is known).
- **Audit**: `platform.support_macro.create` / `.update` / `.delete`, target type `support_macro`, target id = macro id, diff = field changes and the body **length** (`macroAuditDiff`) — never the body text. Deleting needs the explicit confirmation of the dialog (`confirmation_required`).

### Desk settings (`/ops/support/settings`, `/ops/support/settings/general`; `platform.sla.manage` — admin only)

- **Storage and precedence**: the `support_settings` singleton (`id = 1`; a missing row means the schema defaults and the page says so; the first save creates it, `metadata.created`). - **Round robin** (`auto-assign.ts` — `chooseRoundRobinAssignee`, `resolveAutoAssignee`, `autoAssignNewTicket`; re-exported by `settings.ts`): among the operators (`PLATFORM_SUPPORT` / `PLATFORM_ADMIN`) online — one rule for the desk since the integration pass: a bell poll of the console or a ticket-page heartbeat within `AGENT_ONLINE_MS` (5 minutes, `ONLINE_WINDOW_MINUTES`; `listOnlineAgents` in notifications.ts, §14) — the one holding the fewest open tickets (`new` / `open` / `pending` / `on_hold`), then the one whose assigned tickets moved least recently, then by name. ## 12. Ticket detail (task T2: page `/ops/support/[id]`, components `components/ops/support/ticket/**`, loaders `server/support/ticket.ts`, presence `server/support/presence.ts`, actions `server/ops/actions/support-ticket.ts`, routes `/api/support/attachments` + `/api/support/attachments/[id]`; namespace `support-ticket` × 6)

The page (`platform.tickets.read`) shows the conversation merged with the timeline events (oldest first; events before messages of the same instant), the composer, the properties panel, the SLA panel, the presence banner, the requester sidebar and the satisfaction rating. Every mutation is a server action with `requirePlatform("PLATFORM_SUPPORT", permission)`, zod, `withPlatform`, `support_events` rows and an `auditPlatform` entry in the same transaction; a read-only role sees the page without the composer and the controls (`platformCan`).

### Workflow matrix (`TICKET_TRANSITIONS`, `canTransitionTicket`)

| From       | To                                         |
| ---------- | ------------------------------------------ |
| `new`      | `open`, `pending`, `on_hold`, `solved`, `spam` |
| `open`     | `pending`, `on_hold`, `solved`, `spam`     |
| `pending`  | `open`, `on_hold`, `solved`, `spam`        |
| `on_hold`  | `open`, `pending`, `solved`, `spam`        |
| `solved`   | `open` (reopen), `closed`                  |
| `closed`   | `open` (reopen)                            |
| `spam`     | `open` (restore)                           |

- **Confirmed transitions** (`CONFIRMED_TICKET_TRANSITIONS` = `spam`, `closed`): the action answers `confirmation_required` without `confirmed: true`; the properties panel confirms them in a dialog, and the composer's split button never offers them (`COMPOSER_STATUSES` = `open`, `pending`, `on_hold`, `solved`, filtered by the matrix). The spam dialog names the side effect: marking a ticket as spam **blocks the sender** (§4 "Blocked senders" — further mails become spam tickets and are never answered automatically) until the ticket is reopened, which lifts the block.
- **Composing is blocked** on `spam` tickets (`COMPOSE_BLOCKED_STATUSES`) and on merged tickets (`invalid_state`); the composer says why and links the merge target.
- **Agent replies and the status**: the first agent reply on a `new` ticket moves it to `open` unless the operator (split button) or the macro chose a status — `status` event with `reason: "agent_reply"`. An agent reply never reopens a solved or closed ticket by itself (a "thanks, glad it works" keeps the ticket solved); "Send & mark as open" reopens deliberately, and a customer reply reopens on its own (§4 step 7, the portal). Internal notes change no status.
- **Macros** (§11 contract): the macro text lands in the editor with the placeholders substituted (`{{ticket.number}}`, `{{requester.first_name}}`, `{{requester.email}}`, `{{agent.name}}`, `{{organisation.name}}` / `{{organization.name}}` and the `{snake_case}` forms of §11; unknown tokens stay visible); its actions (`status`, `priority`, `tags_add` / `tags_remove`, `assign_to_self`) are applied on sending when the checkbox is on, through the same workflow checks; `usage_count + 1`.
- **Merge** (`mergeTicketAction`, confirmed, by ticket number): the source is closed with `merged_into_id` and a `status` event `reason: "merged"` — **without `resolved_at`** (the target answers the request, so a merged ticket never counts as resolved in the reports, which count `resolved_at`); `closed_at` is stamped; both tickets get a `merged` event and an audit entry; messages stay where they are. A merged, spam or identical target is refused (`invalid_target`), and so is a target of **another organisation** — `merged_into` and the `merged` events are customer-visible on both sides (§3), so the link never crosses tenants (tickets without organisation may join either side; the same rule as the queue's bulk merge). A merged ticket stays closed: `setTicketStatusAction` (and therefore reopen) answers `invalid_state`, so `merged_into_id` is never left on an open ticket. No split.

### Pause, reopen and the SLA clocks (the engine's `statusTransition`, `applyPolicyOnPriorityChange`, `slaClockState` — §10; the panel's `slaView`)

- Every status change on the ticket page — the split button, a macro, the property action, a merge — goes through `applyTicketChanges` → the SLA engine's `statusTransition(policy, ticket, to, now)` with the ticket's own policy, the same call the bulk dialog, the portal (`insertCustomerReply`, `markTicketSolvedAction`) and the inbound handler make: `pending` stamps `paused_at`; leaving it books `pause_total_ms += now − paused_at` and shifts the running due times (`first_response_due_at` while unanswered, `resolution_due_at` while unresolved) by the **business minutes** of the pause — a pause from Friday 17:00 to Monday 10:00 moves them by two hours, not 65 (a 24 × 7 policy: by exactly `pause_total_ms`); the `status` event carries `pauseEndedMs` (wall clock).
- `solved` stamps `resolved_at` and flags a late resolution; `closed` stamps `closed_at` (and `resolved_at` when the ticket was still open — except for a merge, where `withoutResolution` drops the stamp and the flag). A **reopen** (`solved` / `closed` → a working status) clears both, resets `breached_resolution`, counts `reopen_count` and **restarts the resolution clock from now** with `computeDueDates` — and the first-response clock while nobody answered; null without a policy. The `reopened` event carries `count` and the new `resolutionDueAt`.
- A **priority change** is `applyPolicyOnPriorityChange`: every running clock moves by the difference between the old and the new target in business minutes, so absorbed pauses stay absorbed and a reopened ticket created days ago keeps measuring from its reopening (a reopen in the same call is applied first); a shorter target can be overdue at once, a longer one is not. Without a policy the due times are null.
- **States** (`slaView`, from the engine's `slaClockState`): `none` (no due time), `met` / `late` (completed; a merged ticket's resolution clock ends at its closing), `paused` (remaining frozen at `paused_at`), `breached` (past due or the worker's flag), `warning` (= the engine's `due_soon`: the remaining business minutes at or under the policy's unwarned share of the target — exactly when the worker writes `sla_warning`), `on_track`. `resolutionRestartedAt` (the last `reopened` event of the timeline) is shown in the panel, never measured against. Remaining times tick client-side from the server's figure; nothing is estimated.

### Presence and collision detection (`support_presence`)

`presenceHeartbeatAction` every **15 s** (`PRESENCE_HEARTBEAT_MS`) upserts `(ticket_id, user_id) → last_seen_at, mode` — `typing` while the composer changed within the last 10 s (a typing burst sends one heartbeat at once), else `viewing`; hidden tabs skip the beat, a visible tab beats immediately. Rows older than **45 s** (`PRESENCE_STALE_MS`, three missed beats) are dropped by the loader and pruned locally on every tick — also when the heartbeat fails (session expired, network gone), so the server-rendered list never outlives the window; the local pruning measures on the **server's clock** (`generatedAt` of the render, then `now` of every heartbeat, plus the time elapsed since), never on the browser's, so a skewed browser clock neither hides everyone nor keeps them. Leaving the page removes the row (`presenceLeaveAction`, after a heartbeat still in flight settled so its upsert cannot resurrect the row); rows nobody refreshed for an hour are purged opportunistically (the SLA worker owns the scheduled expiry). Heartbeats are not audited. The banner: "Marco is typing…" / "Marco is viewing this ticket." + "Agree who answers before both of you reply." The assignee list's online dot = a heartbeat on any ticket within 5 minutes (`OPERATOR_ONLINE_MS`).

### Two-phase compose and sending

1. `composeTicketMessageAction({ ticketId, mode, body, status?, macroId?, applyMacroActions?, attachments? })`: Markdown subset → sanitised HTML + plain text, threading ids (`In-Reply-To` = the customer's last message id, `References` = the chain), `Message-ID` stored before sending; replies stamp `last_agent_message_at` and — the first one — `first_responded_at` (+ `breached_first_response` when late); an unassigned ticket is taken over by the author; the status / macro changes go through `applyTicketChanges` (one UPDATE, one event per changed field); `reply` / `note` event with `messageId`, attachment count, macro id, `firstResponse`, `pendingUpload`. Outbound messages are stored `queued`, notes `na`. Without attachments the reply is sent at once.
2. Attachments: the page posts each file to `POST /api/support/attachments` (`platform.tickets.write`; **gate** `assertMessageAttachable`: the caller's own message, a `queued` outbound message or a note younger than 15 minutes, fewer than 5 files so far; `screenAttachments` limits + a signature check for binary types, sanitised file name, `sha256`, the no-op scanner hook — files stay labelled "not scanned"; stored as bytea with the ticket's organisation id). When any upload is refused or lost, the composer does **not** call step 3: the reply stays `queued` ("Message stored" + the refused files), and the operator decides in the timeline ("Send now") — a customer never receives "screenshot attached" without the screenshot.
3. `finalizeTicketMessageAction({ messageId })` → `deliverMessage`: **one transaction that claims the row** — `SELECT … FOR NO KEY UPDATE SKIP LOCKED` on the message; a locked row (a send in flight from another operator's "send now" or a retried compose) answers `unchanged`, an already `sent` row too — then `sendTicketMail` (§4) with the stored files, `delivery_status` → `sent` (+ `provider_message_id` from Resend) or `failed` + `delivery_error` (visible in the timeline with "Send again"), audit `platform.support_ticket.send` (`ok`, `transport`, error text ≤ 200 chars, attachment count, locale — no body). The lock spans the transport call (bounded by its timeout) and blocks only concurrent writes to this one message.
4. Downloads: `GET /api/support/attachments/[id]` re-checks `platform.tickets.read`, loads through `tracksite_ops`, audits the download (`platform.support_ticket.attachment_download`, ids only) and serves `Content-Disposition: attachment` with `X-Content-Type-Options: nosniff`, a sandboxed CSP and no caching.

### Requester sidebar

Requester (address, name, language, linked account, channel, the original contact request when converted from the Inbox), organisation (name, slug, suspended flag, plan, subscription state from `subscriptions.status`, this month's billable events against the limit — metadata only), links to `/ops/organisations/[id]` and `/ops/break-glass?organization=…`, the five most recent other tickets of the organisation or address, five recent `audit_log` entries (action + actor kind; **an admin sees the organisation's trail, a support agent their own actions on it** — `recentAuditScope`, consistent with `platform.audit.read` "own actions only" in §2) and the CSAT answer.

## 13. Ticket list — queue, views, bulk actions (task T1: `/ops/support`, `apps/web/src/server/support/tickets.ts` + `views.ts`, actions `apps/web/src/server/ops/actions/support-tickets.ts`, components `apps/web/src/components/ops/support/list/**`, saved views `/ops/support/views`, `/new`, `/[viewId]`; namespace `support-tickets` × 6)

Cited from the code as docs/18 §"Ticket list". ### URL model (`views.ts`)

- `view=<default key | saved view id>` selects the **base** (a filter set + sort); every other parameter is an **override** on top of it, so a view can be refined without losing it and links stay short (`ticketQueryString` writes only the differences from the base). Absent parameter → the view's value; the literal `any` → no filter (`status=any`, `assignee=any`, `tags=any`, `plan=any`, `sla=any`, `from=any`, `to=any`, `lastDays=any`); `dates=any` lifts the view's whole date range (`from`, `to`, `lastDays`) at once — the filter form's "Ignore the view's date range" checkbox, needed because an empty date input means "as in the view"; own date values in the same URL still win. Invalid values fall back to the view, then to the neutral set (`EMPTY_VIEW_FILTERS`) — a bad link never errors and never shows an empty list by accident.
- Without `view`: overrides start from the neutral set; a bare `/ops/support` opens "All open". An unknown saved view id, or another operator's personal view, falls back to "All open" with a warning (`queue.viewMissing`).
- Multi-value lists (`status`, `priority`, `channel`) take comma-separated values; the GET filter form narrows a list to one value or lifts it (`any`) — several values at once are the view editor's job. Date parameters are calendar days (UTC, `YYYY-MM-DD`, real dates only); `lastDays` (1 … 365) wins over `from` / `to` on `dateField` (`created` | `updated` | `resolved`). `q` ≤ 80 characters; `page` ≥ 1 (capped at 10 000); `sort` one of `TICKET_SORTS`.

### Search, sort, pagination, counts, SLA state, presence (`tickets.ts`)

- Search: `ILIKE` (wildcards escaped, substring) over subject, requester name / e-mail, organisation name / slug, plus an exact ticket number for `#1234` / `1234`. `pg_trgm` is not installed by a migration yet; a trigram index is the follow-up (§9).

- SLA state per row from the stored timestamps only (`slaState`): the worker's breach flags win; otherwise the running clock (first response until answered, then resolution until solved) is `paused` (`paused_at` set), `breached` (past its due time) or `on_track`; every clock done → `met`; no due times → `none` ("no SLA policy"). ### Workflow (`TICKET_TRANSITIONS`, `canTicketTransition`)

| From      | Allowed targets                                |
| --------- | ---------------------------------------------- |
| `new`     | `open`, `pending`, `on_hold`, `solved`, `spam` |
| `open`    | `pending`, `on_hold`, `solved`, `spam`         |
| `pending` | `open`, `on_hold`, `solved`, `spam`            |
| `on_hold` | `open`, `pending`, `solved`, `spam`            |
| `solved`  | `closed`, `open` (reopening)                   |
| `closed`  | `open` (reopening)                             |
| `spam`    | `open` (restore)                               |

The matrix is identical to the ticket page's (`ticket.ts`, §"Ticket detail"). `solved`, `closed` and `spam` hide a ticket from the open queues, so the bulk dialog asks for a confirmation (`CONFIRMED_STATUSES`). **Every status change — bulk or from the ticket page — is the SLA engine's `statusTransition(policy, ticket, to, now)` (§10) with the ticket's own policy** (`ticketStatusChange` in `tickets.ts` only adds `reopen_count` and the timeline event kinds; `loadTicketPolicies` fetches the policies of the locked rows in one query): `pending` pauses the clock; leaving it shifts the running due times by the **business minutes** of the pause while `pause_total_ms` books the wall clock (a pause from Friday 17:00 to Monday 10:00 moves the due times by two hours, not 65); `solved` / `closed` stamp `resolved_at` / `closed_at` and flag a late resolution; a reopening clears the stamps, counts, and recomputes the resolution due time — and the first-response one while nobody answered — from the reopening with `computeDueDates`, because the worker only watches tickets that have a due time; `spam` stops every clock without a resolution. A ticket without `sla_policy_id` has no SLA: no due times, and a resume shifts nothing but the wall clock. | ------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| status                    | `platform.tickets.write`  | already in that status, transition not in `TICKET_TRANSITIONS`, ticket merged; the change is `ticketStatusChange` (above); `status` event with `pauseEndedMs`, `reopened` event with the new count                                                                                                                                                                                                                                                                                                                                                                         |
| priority                  | `platform.tickets.write`  | already that priority; the change is `ticketPriorityChange` (`tickets.ts`) — the engine's `applyPolicyOnPriorityChange` (§10) with the ticket's own policy, as on the ticket page: every running clock moves by the difference between the old and the new target in business minutes (absorbed pauses stay absorbed; a clock without a due time so far starts from the creation) and the breach flags follow the new due times, so a shorter target can be overdue at once; **without a policy the running due times are cleared** (they cannot be derived, never guessed), finished clocks keep their stamps. `priority` event `{ from, to }`; the audit diff carries the moved due times (ISO) and the policy id |

The source gets a `status` event (`reason: "merged"`) and a `merged` event `{ direction: "into", ticketId, number, intoNumber }`; the target one `merged` event per source `{ direction: "from", ticketId, number }` — the shape the ticket timeline and the customer portal read; the source conversation stays readable |

## 15. Reports (task T7: page `/ops/support/reports`, export route `/ops/support/reports/export`, module `apps/web/src/server/support/reports.ts`, components `apps/web/src/components/ops/support/reports/**`; namespace `support-reports` × 6)

- **Permission.** `platform.reports.read` (support and admin): the page uses `checkPlatform("PLATFORM_SUPPORT", "platform.reports.read")`, the export route `requirePlatform(…)`; reads run as `tracksite_ops` through `withPlatform`. The page shows aggregates and organisation metadata only, so no break-glass grant and no page-view audit entry is involved; the CSV export is audited (below). Reached from the queue header (`/ops/support` → "Support reports") and by URL.
- **Range (URL model, `parseReportRange`).** `?days=N` (1–`REPORT_RANGE_MAX_DAYS` = 365 calendar days ending today) or `?from=YYYY-MM-DD&to=YYYY-MM-DD` (`to` defaults to today; at most 365 days; never in the future); `bucket=day|week` overrides the automatic choice (weeks from more than `REPORT_WEEKLY_FROM_DAYS` = 60 days). Anything invalid falls back to the last `REPORT_DEFAULT_DAYS` = 30 days with a warning on the page and a 400 on the export. Quick ranges `REPORT_PRESET_DAYS` = 7 / 30 / 90.
- **Calendar.** UTC throughout: days start at 00:00 UTC, weeks are ISO weeks (Monday 00:00 UTC), bucket keys are `YYYY-MM-DD` (the day or the week's Monday; `date_trunc` at time zone UTC in SQL, `bucketKey` in TypeScript), buckets are gap-filled (`bucketsOf`) and marked `partial` when the range or "now" does not cover them (first / last week, today).
- **Cohort.** "Tickets created inside the range": `created_at` in `[start, end)`, `status <> 'spam'`, `merged_into_id IS NULL` (`cohortWhere`). Everything per ticket — times, SLA outcomes, satisfaction, categories, tags, first responders — is a cohort figure. Point-in-time figures (state at generation, independent of the range): backlog by status, open backlog (`OPEN_TICKET_STATUSES` = new, open, pending, on_hold), unassigned open, oldest open, the agents' open tickets. Range-activity figures, whenever the ticket was created: "resolved in range" (`resolved_at` inside the range), agent replies (outbound agent messages by author, inside the range), agent solves (`status` events with `payload.to = 'solved'` by actor, inside the range — a reopened ticket counts again when solved again).
- **Cap.** At most `REPORT_MAX_TICKETS` = 20 000 cohort rows (oldest first, `created_at, id`) are loaded for the per-ticket figures; the first responders are joined to that same sample (a subquery with the same filter, order and cap — `DISTINCT ON (ticket_id)` must order by ticket id, so a cap on the responder query itself would pick a different sample). `cohort.truncated` (`cohortTotal > loaded`) shows a warning naming the affected figures; volume, backlog, replies, solves and organisations are SQL aggregates and always complete. `loadSupportReportSnapshot(tx, range, now, maxTickets)` takes the cap as a parameter for the tests only.
- **Times.** Wall clock from `created_at` to `first_responded_at` (first outbound agent message; an automatic acknowledgement never sets it) and to `resolved_at` (transition to solved), pauses not subtracted — the time the requester experienced; negative differences clamp to 0. Median with linear interpolation (`percentile_cont` semantics); the 90th percentile is withheld below `MIN_P90_SAMPLE` = 10 measured tickets (`p90Withheld`); "pending" counts the cohort tickets without the instant.
- **SLA outcomes (`slaOutcome`, per clock `first_response` / `resolution`).** No due time → `no_policy`. Stopped clock (`first_responded_at` / `resolved_at` set) → `met` or `breached` by the stop instant against the stored due time (which already includes pauses); the worker's `breached_*` flag wins when set. Running clock: flagged → `breached`; `paused_at` set → `running` (a paused clock is never breached by the wall clock, its due time shifts when the pause ends); overdue → `breached`; otherwise `running`. Rate = met / (met + breached) — concluded clocks only; running and no-policy tickets are listed, never rated. Overall and per priority; `withPolicy` counts cohort tickets with any due time.
- **Agents.** One row per user with a platform role (`PLATFORM_SUPPORT`, `PLATFORM_ADMIN`), sorted by name; authors without a platform role any more are folded into one `former` row. First responses attribute a cohort ticket to the author of its first outbound agent message (`DISTINCT ON (ticket_id) … ORDER BY ticket_id, created_at`), with the median first-response time per agent; open now, replies and solves as above; `unassignedOpen` beside the table.
- **Satisfaction.** `satisfaction.score` (1–5) stored on cohort tickets (`satisfactionScoreOf`: anything else is ignored, never guessed): average, distribution 5 → 1, response rate = answers / cohort tickets in `solved` or `closed`; `support_settings.csat_enabled = false` adds a note (existing answers still count).
- **Top lists.** `REPORT_TOP_LIMIT` = 10 categories (trimmed; empty = "without a category") and tags (a ticket counts once per distinct tag, so shares do not add up to 100 %), ranked by count then name, with a "more" count. Busiest organisations: top 10 by cohort tickets with "still open" and "resolved" counts, name and slug from the organisation record only (the organisation page needs its own permission); distinct organisations and tickets of senders without an organisation are counted separately.
- **Small numbers.** Below `SMALL_SAMPLE_TICKETS` = 20 cohort tickets the page shows an info alert ("read the counts, not the percentages"); every rate and median stands next to its sample size (`measured`, `met of counted`, `answers`); nothing is extrapolated or estimated (docs/18 §1).
- **CSV export.** GET form on the page → `/ops/support/reports/export?kind=<summary|volume|backlog|times|sla|agents|csat|categories|tags|organisations>&from&to&bucket` (parsed exactly like the page; a fallback range is refused with 400). Every export writes an audit entry `platform.support_report.export` (target `support_report` / `<kind>`, metadata `module`, `kind`, `from`, `to`, `bucket`, `rows`, `tickets`, `truncated`) in the same transaction as the read — a bulk read that leaves the console is recorded like a mutation. RFC 4180 (`csvCell`: quoting, a leading formula character neutralised), durations in minutes (one decimal), rates with four decimals, counts, ids and labels only; `content-disposition: attachment; filename="support-report-<kind>-<from>_<to>.csv"`, `cache-control: no-store`, `x-robots-tag: noindex`.
- **Privacy.** Everything is a count, a duration, a rate or an id / label: no subject, message body, requester name or e-mail address is selected (`ReportTicket`, `FirstResponder`); agents appear by display name; organisations by name and slug.
- **UI.** `OpsPageHeader` with as-of / range / days / tickets context, range form (presets, from / to, bucket, apply / reset), KPI tiles, the volume chart (recharts `ComposedChart`: stacked bars per channel + resolved line, `aria-hidden`, reduced motion honoured) with the same values in a table (`TableDisclosure`), CSS share bars and tables for backlog, times, SLA by priority, agents, satisfaction distribution, categories, tags and organisations (`@track-site/ui` `Table` with a `label` on every `Td`, so rows stack into cards below 48 rem), a "Method and caveats" list (`MethodNotes`), 44 × 44 targets, no nested interactive elements; strings in `support-reports.json` × 6 (`supportReports.*`), vocabulary from `support.*`.
- **Verification (T7).** `reports.test.ts` (constant mirrors, calendar helpers, range parsing and query round-trip, buckets, percentiles and the p90 threshold, `slaOutcome` matrix, every reducer, small-sample / truncated flags, CSV quoting and every section), `reports.integration.test.ts` (loader as `tracksite_ops`: volume by bucket and channel, solved series, cohort exclusions, first responders and their instants, agent counts, backlog, organisations; capped sample keeps the first responders on exactly the loaded tickets; ISO-week buckets and range boundaries), `pnpm --filter @track-site/web typecheck`, `test` (namespace parity `support-reports` × 6), eslint on the changed files.
