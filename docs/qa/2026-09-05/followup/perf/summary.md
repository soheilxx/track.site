## 5. What bounds the simulated LCP now

Lighthouse computes the mobile LCP with Lantern from an **unthrottled** trace. The LCP graph keeps every network request that finished before the observed paint except low-priority images (`@paulirish/trace_engine/models/trace/lantern/metrics/LargestContentfulPaint.js`: `isNotLowPriorityImageNode`; `FirstContentfulPaint.getFirstPaintBasedGraph` drops only requests that ended after the cutoff and scripts whose first `EvaluateScript` task started after it). On localhost every hydration script and both fonts finish within ~60–200 ms, before the first paint (~190 ms in most traces), so they are simulated on the 1.6 Mbps link ahead of the LCP although they are `async` and the text paints without them in a real browser. Per representative after-run (`lcp-graph-after.md`, from the `network-requests` audit and `observedLargestContentfulPaint`):

Consequences:

- The floor of the simulated LCP is set by the framework (131.2 KB gzip), the fonts (Inter 49 KB preloaded, Bricolage 42 KB discovered from the CSS; both finish before the paint) and the render-blocking CSS (21.6 KB): ≈ 330–365 KB on a 1.6 Mbps link (≈ 1.7 s of transfer) plus round trips plus the 4 × slowed script parsing/execution. The document and the route chunks — the parts this task could change — are now 40–50 KB and 55–63 KB of that graph. Removing the fonts or the framework from the graph is not possible without dropping the fonts or the App Router, so **LCP ≤ 2.5 s is not reached in this lab profile**, while FCP and the document itself improved by the full amount of the removed bytes (§2).
- The lazily loaded chunks (hero demo 9.4–10.3 KB, finder/calculator 13.4 KB gzip) start after the observed paint in every after-trace ("Requests after it" above) and are therefore outside the LCP graph — deferring them helps the simulation exactly because of that, while the total JavaScript per page load barely changes.
- Run-to-run noise: in some traces the headless shell paints ~1.0–2.2 s after `load` (`observedFirstContentfulPaint` 1 179–2 231 ms instead of ~190 ms — before: pricing runs 1/2, hub run 1; after: home runs 1/3, article run 1; `observed-paint-per-run.txt`). Such a run pulls the deferred chunk and the RSC prefetches into the graph and reports a higher Speed Index and TBT (the `/en` SI 2.35 s and TBT 57 ms medians in §2 come from two such runs; the third run has SI 1.36 s / TBT 38 ms). Medians of three runs absorb one such run per page; the article's median LCP (3.02 → 3.35 s) lies inside its before spread (2.71–3.73 s).
- Experiments not kept (analysis builds, 1 run each, `lighthouse-variant-linkcss/` vs `lighthouse-variant-inlinecss/`): `experimental.inlineCss` removes the two render-blocking requests but embeds the stylesheet in the head **and** in the RSC payload (`<style>` 115 221 B plus the same text in the flight data), so the document grew from 40.5 to 80.0 KB transfer on `/en`, the RSC prefetches from 27 to 49 KB, and LCP did not improve (3.44 → 3.80 s `/en`, 2.86 → 3.50 s hub, 3.44 → 3.29 s article, 3.48 → 3.48 s pricing); it stays off. The Turbopack tree-shaking flags produced byte-identical output (`bundle-attribution-treeshake.md`).
