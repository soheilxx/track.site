# 17 - Track Operations console

Status: foundation (task O0, 2026-09-08 — access model, migration 0014, shell, bootstrap CLI) plus all ten module slices (Organisations, Break-glass, Platform health, Revenue, Controls, Inbox, Growth, Audit, Platform users, Content), the Support desk module (docs/18 — tickets, views, macros, reports, settings, the SLA worker; hardened 2026-09-09, docs/18 §18) and the integration pass (task I, 2026-09-08: one session guard for suspension + read-only support access, shell entry points, journal/seed/docs, full gates — §10). Each module documents its own rules here; §10 lists the cross-module rules and the open follow-ups.

## 1. Purpose

`/ops` is the internal console of Track's own operators: platform-wide status, tenant metadata, kill switches, break-glass access, revenue and growth aggregates, the public-form inbox, platform announcements (under Controls), the Tracking Knowledge editorial board and the platform audit log. It is deliberately not part of the customer dashboard (`/app`): a separate shell, a separate database role and a separate, stricter access model (docs/03 §B8).

Binding product rules for every module:

- **No raw data by default.** The console never shows raw event payloads, personal data of end users (visitors of customer sites) or secrets. Aggregates and metadata only — unless the operator holds an approved, active break-glass grant for that organisation, and even then the view is read-only and every page view is audited with the grant id.
- **Every mutation is a server action** with `requirePlatform(role)`, zod validation, `auditPlatform` (organisation id of the affected tenant when applicable, actor kind `platform`) and an explicit confirmation in the UI for risky actions (suspend, kill switch, flag flip, role grant, break-glass approval).
- **Four eyes** for granting platform roles and for break-glass approval whenever a second platform admin exists. Single-admin fallback: mandatory ticket reference + reason, recorded as self-approved.
- **Honest states.** Empty, partial and stale states are shown as such; nothing is invented (no fake metrics, no "n/a" dressed up as a number).
- **UI**: WCAG 2.2 AA, keyboard operable, 44 × 44 targets, no nested interactive elements, semantic colour always with text/icon, dense tables with mobile stacking, six-locale strings in the module's namespace, formats through `apps/web/src/lib/format.ts`.

## 3. Access model

### Roles

`user.platform_role` (packages/core `PLATFORM_ROLES`): `NONE` (every customer), `PLATFORM_SUPPORT`, `PLATFORM_ADMIN`. Platform roles are orthogonal to organisation membership; operators are not members of customer organisations (the seeded dev admin is not a member of `acme-demo`). The column is never editable through the public API (`input: false` in better-auth); it changes only through the `ops:grant` CLI (bootstrap) and, later, the Platform users module (four eyes).

### `apps/web/src/server/ops/platform.ts`

| Helper                                                                                          | What it does                                                                                                                                                                                                                                                                                                    |
| ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `platformGate()`                                                                                | Per-request resolution of the operator. Signed out → redirect to `/<locale>/login?next=/ops…`. No platform role → `no_role`. Two-factor missing while the step-up rule applies → `two_factor_required`. The layout renders the localized 403 page for both instead of the shell; the page component never runs. |
| `requirePlatform(minRole)`                                                                      | For pages and server actions: returns `PlatformContext { user, platformRole, actor, requestId }` or throws `PlatformAccessError` (`no_role`, `two_factor_required`, `insufficient_role`). `PLATFORM_ADMIN` satisfies `PLATFORM_SUPPORT`. `checkPlatform(minRole)` is the non-throwing form for inline 403s.     |
| `withPlatform(ctx, tx => …)`                                                                    | Transaction with `SET LOCAL ROLE tracksite_ops` (BYPASSRLS). The only way the web app assumes the operator role; requires a `PlatformContext`; records nothing by itself.                                                                                                                                       |
| `auditPlatform(ctx, { action, organizationId?, targetType, targetId?, diff?, metadata? }, tx?)` | Append-only `audit_log` row with actor `{ kind: "platform", userId, email, platformRole }` (redacted), `organization_id` of the affected tenant or null, the request id and `metadata.platformRole`. The HTTP status of the rendered 403 page is 200 (Next's `forbidden()` interrupt needs `experimental.authInterrupts`, which is not enabled); the page is `noindex`, never cached, and contains nothing but the explanation.

### Two-factor requirement (step-up)

Platform pages require the operator's two-factor authentication (better-auth `twoFactorEnabled`) to be enabled. `OPS_REQUIRE_2FA=false` disables the check for local development only (`.env` / `.env.example` carry it as `false` with a comment); `APP_ENV=production` always requires two-factor. An operator without two-factor sees the localized "enable two-factor authentication first" page, which links to the self-service enrolment below (`/app/settings/security`) next to the way back to the dashboard.

### Enrolment (self-service, `/app/settings/security`)

Every account — customers and operators alike — enrols, disables and renews two-factor on the Security page of the customer dashboard (`apps/web/src/app/app/settings/security/page.tsx`, components under `components/app/settings/security/`, namespace `security` × 6). The page needs a session but no organisation membership, so an operator who is no member of any tenant (the seeded `ops@acme.test`) enrols there as well; it is reachable from the settings sub-navigation, the account menu ("Security") and the Ctrl/Cmd+K palette ("Security settings").

| Flow             | What happens                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Status card      | Enabled / not enabled (from the `user` row, not the cookie cache), "enabled since" (the newest `user.two_factor.enabled` audit row of the account) and the number of unused backup codes (counted server-side through better-auth's server-only `viewBackupCodes`; the codes never reach the page). Accounts with a platform role see the note that Track Operations requires two-factor and, once enabled, the link back to `/ops`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Enable           | Password confirmation → server action `startTwoFactorEnrolment` (`auth().api.enableTwoFactor` with the request headers) → the otpauth URI rendered as a QR code (client-side encoder `qr.ts`, no dependency, no network; dark on white in both themes) plus the manual base32 key in groups of four → six-digit code → `confirmTwoFactorEnrolment` (`auth().api.verifyTOTP`), which is the moment better-auth switches the account to two-factor and rotates the session (the new cookie reaches the browser through the `nextCookies` plugin) → backup codes shown once with copy, download as `.txt` and the "I stored them" checkbox that gates "Done".                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Disable          | Password plus an explicit confirmation → server action `disableTwoFactor` (`auth().api.disableTwoFactor`: better-auth deletes the secret and the backup codes, forgets trusted devices and rotates the session).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| New backup codes | Password → server action `regenerateBackupCodes` (`auth().api.generateBackupCodes`); the previous codes stop working, the new ten are shown once with the same copy/download/confirmation block.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Audit            | Every state change runs through the four server actions in `apps/web/src/server/actions/security.ts`; the client never claims a change. An action checks the session, a budget of six calls per minute per account (better-auth's `/two-factor/*` limit covers HTTP calls only, not `auth().api`), the stored `user.two_factor_enabled` flag (an enrolment on an enabled account, a confirmation or a disable that has already happened is refused as `state`, so a repeated call can never add a second row) and the credential account (`noPassword` for an account without a password — see below), calls better-auth, re-reads the flag and writes the row only for the change better-auth actually made: `user.two_factor.enabled` / `user.two_factor.disabled` / `user.two_factor.backup_codes_regenerated`, target type `user`, diff `{ twoFactorEnabled }` — never a secret, URI or code. The organisation context is resolved before the session rotates, so members write into the active organisation's audit log (tenant transaction, session actor); an account without a writable tenant context (operator without membership, read-only support session) writes without organisation as the platform actor, so `/ops/audit` lists it. A failed insert is reported on the page (`errors.audit`) without hiding the change. |

Accounts without a credential account (a passkey- or OAuth-only account, should such sign-ups be added; today every account is created with e-mail and password) cannot confirm a password, and better-auth (`allowPasswordless` off) would answer `INVALID_PASSWORD`. The actions detect the missing credential account first and answer `noPassword`, whose message points to the password reset, which creates the credential account (`resetPassword` in better-auth).

The spec signs in on its own (no stored session) and leaves the seeded owner alone: the enrolment rotates only the e2e account's session, and while its two-factor is on, only that account's password sign-ins land on the two-factor page.

### Database role `tracksite_ops`

Migration 0014 creates `tracksite_ops` (`NOLOGIN BYPASSRLS`) with exactly the privileges of `tracksite_worker` (all tables, all sequences, default privileges for future tables) and grants it to the migration owner. Platform reads bypass RLS **only** through `withPlatform`; the tenant helpers (`withOrg` / `withTenant` → `tracksite_app`) stay RLS-enforced. The read-only rule of the console is enforced in the application (server actions, product rules), not by the role's privileges.

## 4. Break-glass rules

Table `break_glass_access` (baseline + migration 0014): `organization_id`, `platform_user_id` (grantee), `reason` (mandatory), `ticket_ref`, `approved_by`, `approved_at`, `mode` (`read_only` — the only mode), `starts_at`, `ends_at` (`CHECK ends_at > starts_at`), `revoked_at`, `customer_notified_at`. The table is revoked from `tracksite_app` (tenants never read it directly).

- A grant is **active** only when `approved_at` is set, `revoked_at` is null and now ∈ [`starts_at`, `ends_at`).
- **Time-boxed**: the Break-glass module caps the window (recommendation ≤ 4 h, hard maximum 24 h) and shows the remaining time in the shell while a grant is active.
- **Justified**: reason mandatory; ticket reference mandatory when self-approved.
- **Four eyes**: `approved_by` is a _different_ platform admin when a second admin exists; otherwise self-approval with ticket + reason, recorded as such (`approved_by = platform_user_id`).
- **Step-up**: the operator must have two-factor (see above); the approval action is a confirmed server action.
- **Audited**: request, approval, revocation, expiry and every tenant-detail page view (`metadata.breakGlassId`) are `audit_log` rows with the organisation id, so the customer's own audit log (`/app/team/audit`) shows the operator access.
- **Customer notification**: `customer_notified_at` records when the organisation's owners were told (the Break-glass module sends the mail).
- **Read-only**: even under an active grant the console never mutates tenant data on the operator's behalf and never shows secrets or raw payloads; PII fields of end users stay redacted.

Kill switches (docs/03 §B8): global `KILL_SWITCH_GLOBAL` (collector 503), per organisation `organization.suspended_at` / `suspended_reason` (migration 0014; the Controls module flips it, the dashboard and API answer 403 for its members until the suspension is lifted), per site/environment/connector in the customer settings.

## 6. Worker heartbeats

`apps/worker/src/jobs/index.ts` upserts `worker_heartbeats` after every job run (as `tracksite_worker`): `last_run_at` (finish time), `last_ok_at` (moves only on success), `last_error` (first 1000 characters), `last_duration_ms`, `host`. A heartbeat that cannot be written (database down, migration not applied) is logged once per job at warn level and never affects the scheduler. Platform health shows a job as stale when `last_run_at` is older than twice its interval and as failing when `last_run_at > last_ok_at`.

## 7. Bootstrap: granting the first admin

```bash
pnpm --filter @track-site/db ops:grant --email <address> --role PLATFORM_ADMIN   # or PLATFORM_SUPPORT | NONE
pnpm --filter @track-site/db ops:users                                             # who has a platform role
```

`ops:grant` refuses to run without an explicit `--email`, requires a verified e-mail for a non-NONE role, refuses to demote the last `PLATFORM_ADMIN` unless `--force` is given, writes an audit entry (`platform.role.set`, actor `system` / `cli:ops-grant`, diff before → after) and prints the result without secrets. The person signs up as a normal user first; the role is granted afterwards.

**Production** (docs/07 §"Operator access"): run the command through the prod-env wrapper so the database URL never appears in a shell history or chat transcript — `vercel env pull` into a scratch env file outside the repository, then `node <scratch>/run-with-prod-env.mjs pnpm --filter @track-site/db ops:grant --email <owner address> --role PLATFORM_ADMIN` (the wrapper loads the pulled variables into the child process and prints nothing but the command's output). Migration 0014 must be applied first (`… run-with-prod-env.mjs pnpm db:migrate`). The account then enrols two-factor and signs in at `https://www.track.site/ops`.

**Local**: `SEED_DEMO=true pnpm db:seed` creates `ops@acme.test` / `Demo-Password-123!` (PLATFORM_ADMIN, no two-factor — fine with `OPS_REQUIRE_2FA=false` in `.env`; the seed refuses to run with `APP_ENV=production`).

## 9. Content — Tracking Knowledge editorial board (task O10)

`/ops/content` is a **read-only** view of the Tracking Knowledge area: the articles live in git (`apps/web/content/knowledge`, read through the public loader `lib/knowledge.ts`), so the module has no server actions — content changes are commits, not console actions. Five sections, all `checkPlatform("PLATFORM_SUPPORT")`, strings in namespace `opsContent` (`apps/web/messages/<locale>/ops-content.json` × 6), loaders in `apps/web/src/server/ops/content.ts`:

| Path                        | Section                                                                                              |
| --------------------------- | ---------------------------------------------------------------------------------------------------- |
| `/ops/content`              | Editorial board — one row per translation group, status per locale from the front matter             |
| `/ops/content/feedback`     | Reader feedback ("Was this article helpful?") per article, all-time and recent, per locale           |
| `/ops/content/paths`        | Learning paths from `content/knowledge/paths.<locale>.json`: listed vs. resolved ids, hub visibility |
| `/ops/content/freshness`    | Sitemap and feed counts as the loader would render them now, last build (`.next/BUILD_ID`)           |
| `/ops/content/integrations` | Integration catalogue coverage: which entries have published articles per locale and vendor docs     |

Rules (all derived from front matter, never invented):

- A translation group is **complete** when every active locale has a `published` version; the board counts published / translated / reviewed per locale.
- The **last review** of a version is `reviewedAt`, else its publication date (the first review). A published version whose last review is older than `REVIEW_STALE_DAYS = 180` days is **stale**; drafts and unpublished versions are never stale.
- A version without a `takeaways:` list is flagged **missing takeaways**.
- A group **needs attention** when it is incomplete, has a stale review or a version without takeaways. Filters (view, topic) live in the URL.
- Feedback totals are all-time and the last `FEEDBACK_WINDOW_DAYS = 30` days, split by locale, joined with the board for titles and links. The votes are anonymous by design — there is nothing to drill into; shares are shown only when there are votes.
- Integration coverage uses the same matching rule as the public integration page (`relatedKnowledgeFor`: platform / shop-system slug or knowledge tag); entries with the fewest articles come first.

No tenant data is involved anywhere in the module (articles are public content, `knowledge_feedback` carries no PII and no organisation), so no break-glass grant and no page-view audit entry apply; there are no mutations and therefore no `auditPlatform` rows. Feedback aggregates are read as `tracksite_ops` via `withPlatform`. Honest states: when `knowledge_feedback` is missing (migration 0005 not applied) the feedback page reports "not available" instead of zeros; without a build output (development) the freshness page shows the build as unknown rather than a time; unresolved learning-path ids and never-reviewed groups are listed as such.

Verification: `apps/web/src/server/ops/content.test.ts` (links, front-matter helpers, board rows and filters, feedback rows, learning paths, integration coverage, build info) and `content.integration.test.ts` (feedback loader against the test database as `tracksite_ops`); namespace parity `opsContent` × 6.

## 11. Platform users — operators, four eyes, customer directory (task O9)

`/ops/users` is admin-only (`checkPlatform("PLATFORM_ADMIN")` on every page); strings in namespace `opsUsers` (`ops-users.json` × 6), loaders in `apps/web/src/server/ops/users.ts`, actions in `apps/web/src/server/ops/actions/users.ts`. Every action re-checks `PLATFORM_ADMIN` through `requirePlatform`, validates with zod (hidden `confirm` field = the UI confirmation), locks the affected `user` row (`FOR UPDATE`), re-applies the rules at decision time and writes its `auditPlatform` row (target type `user`, no organisation) in the same `tracksite_ops` transaction. Reads are metadata only: names, e-mails, platform roles, two-factor and verification state, organisation memberships and roles, session counts and timestamps — never session tokens, IP addresses, user agents, passkey material or end-user data.

| Section               | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Role changes          | Four eyes: a change filed by one admin (`platform.role.propose`) is applied by a _different_ admin (`platform.role.set`, the action name the `ops:grant` CLI writes too) who is neither the proposer nor the affected account. Eligible deciders are admins with a verified e-mail and, while the step-up applies, two-factor (`eligibleAdminIds`). An admin never changes or decides their own role (declining one's own demotion included), the last `PLATFORM_ADMIN` is never demoted, a role above `NONE` needs a verified e-mail, one open request per account. |
| Single-admin fallback | Only when no other eligible admin exists at all: the change is applied at once, recorded as self-approved (`metadata.selfApproved`), ticket reference and reason mandatory. With exactly two eligible admins, one changing the other is refused (`needsThirdAdmin`) — a third admin is granted first (regular four-eyes request) or the `ops:grant` CLI is used — so no admin can remove the only other admin and then grant roles alone.                                                                                                                            |
| Requests              | Live in the audit log itself (`propose` rows without a resolving `set` / `decline` / `withdraw` row naming them in `metadata.requestId`); they expire after seven days, turn `stale` when the account's role changed meanwhile (CLI or another request), and are withdrawn by the proposer or declined by any other admin except the affected account.                                                                                                                                                                                                               |
| Forced sign-out       | Every applied role change deletes the account's stored `session` rows in the same transaction and records the count; better-auth's cookie cache can keep a stale session alive for up to `SESSION_CACHE_MINUTES` (5), which the UI states. "Sign out everywhere" (`platform.sessions.revoke`, reason mandatory, confirmed) exists for operator accounts only.                                                                                                                                                                                                        |
| Customer directory    | `/ops/users/directory` and `/ops/users/<id>`: read-only metadata (search, kind, two-factor, sort, counted pagination in the URL); customer accounts have no console action beyond granting a platform role under the rules above.                                                                                                                                                                                                                                                                                                                                    |

Operators enrol two-factor themselves on `/app/settings/security` (§3 "Enrolment"). Verification: `apps/web/src/server/ops/users.test.ts` (verdicts, request state, filters, request-row parsing) and `users.integration.test.ts` (propose → apply with forced sign-out, duplicate, withdraw / decline, `needsThirdAdmin`, single-admin fallback, session revocation, directory and detail loaders as `tracksite_ops`); namespace parity `opsUsers` × 6.

## 12. Two-factor reset

A person who lost their authenticator and their backup codes cannot sign in and cannot disable two-factor themselves; an administrator resets it for them. One routine serves both consoles — `resetTwoFactor()` in `apps/web/src/server/security/two-factor-reset.ts`, run inside the caller's transaction — and the rules are the same everywhere: never the acting admin's own account, always a confirmation dialog with a reason, always an audit entry, always an e-mail to the affected person.

| Rule              | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| What a reset does | Deletes the account's better-auth `two_factor` rows (TOTP secret and backup codes — the plugin keeps them in its own table), sets `user.two_factor_enabled = false`, deletes every stored `session` row (forced sign-out everywhere; the cookie cache can keep a stale session for up to `SESSION_CACHE_MINUTES`), writes the audit entry — all in one transaction. The person then signs in with the password alone and enrols again on `/app/settings/security`. Refused when the account has neither the flag nor a `two_factor` row (nothing to reset).                                                                                                                         |
| Platform users    | `/ops/users` (operators table) and `/ops/users/directory`, `PLATFORM_ADMIN` only (`requirePlatform("PLATFORM_ADMIN")`, `withPlatform`, `auditPlatform`; action `resetTwoFactorAction` in `server/ops/actions/users.ts`). Another platform user: reason mandatory, ticket optional. The admin's own account is refused (`selfTwoFactor`) — another admin resets it. An operator without two-factor is locked out of the console (§3 step-up) until enrolled again.                                                                                                                                                                                                                   |
| Customer accounts | Support tool in the directory for accounts without a platform role: reason **and** ticket reference mandatory and, when the account belongs to organisations, the ticket's organisation (chosen in the dialog, verified against the memberships) — recorded as `audit_log.organization_id`, so the entry also appears in that organisation's own audit log as "Track support" (actor kind `platform`). Accounts without any membership are recorded without an organisation.                                                                                                                                                                                                        |
| Team & Access     | `/app/team` member row, permission `members.security` (OWNER, ADMIN; `packages/core/src/rbac.ts`, helper `canResetTwoFactor`), action `resetMemberTwoFactorAction` in `server/actions/team.ts`: `requireOrgContext("members.security")` plus `assertOrgWritable` (a read-only break-glass session never resets), members of the own organisation only, never oneself, an OWNER only by an OWNER, never a member who holds a platform role (`platformAccount`: a Track operator is reset in Track Operations only — tenant roles never lock an operator out of `/ops`). Runs as `tracksite_app` inside `withOrg`; the audit row goes through `recordAudit` with the organisation id. |
| Audit fields      | Platform: action `platform.two_factor.reset`; team: `member.two_factor.reset` (category "team" in the customer log). Target type `user`, target id = the affected user id, `organization_id` as above, `actor` (redacted platform or user actor), `diff.twoFactorEnabled {before, after: false}`, `metadata`: `reason`, `ticketRef`, `secretsRemoved`, `sessionsRevoked`, `forcedSignOut`, `module`, plus `targetRole`/`support` (platform) or `memberId`/`targetRole` (team). **Never** the secret, the backup codes or session tokens.                                                                                                                                            |
| E-mail            | After the commit, `sendTwoFactorResetMail` sends template `twoFactorReset` (`server/mail/templates/<locale>.ts` × 6, placeholders `{actorRole}` — "a Track platform administrator" / "an owner of your organisation" / "an administrator of your organisation", localized —, `{product}`, `{supportLink}` = the contact page in the person's language) to the affected person in their stored locale: what was reset, that they were signed out, how to enrol again, and whom to contact if this was not requested. A transport failure never undoes the reset; the UI says the person has to be informed another way.                                                              |

Verification: `apps/web/src/server/security/two-factor-reset.test.ts` (pre-check, support link) and `two-factor-reset.integration.test.ts` (reset clears secret, backup codes and sessions as `tracksite_ops` and as `tracksite_app`; self-reset refused without a write; unknown account and no-two-factor refused; audit row without secrets; the platform action with ticket / organisation rules and the notification mail; the team action with the owner rule); `packages/core` rbac test for `members.security`; mail-template parity × 6; namespace parity `opsUsers` and `team` × 6.

## 10. Integration (task I): cross-module rules, session guard, entry points

### Session guard (`apps/web/src/server/session.ts`)

One resolver and one gate for the customer dashboard, its server actions and its API routes:

| Step                  | Helper                                 | Outcome                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --------------------- | -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. context            | `getOrgContext()`                      | the active membership — or, for a platform operator who is no member of the organisation, a **read-only support session** under an active grant (`resolveSupportAccess`: the organisation pinned by the `track_support_org` cookie set by the console's "open dashboard" action, or the operator's latest active grant when they have no membership at all). A support session carries `role: "READ_ONLY"`, `readOnly: true`, `breakGlass: { grantId, endsAt }` and an actor of kind `platform` with the grant id; every resolution is audited (`auditSupportView`, `metadata.breakGlassId`) |
| 2. tenant kill switch | `assertOrganizationActive(ctx)`        | `organization.suspended_at` set → `OrganizationSuspendedError` (FORBIDDEN 403, `details.reason = "organization_suspended"`, localized notice from `ops-organisations.json`, also carried as `digest` for the dashboard error boundary)                                                                                                                                                                                                                                                                                                                                                       |
| 3. read-only rule     | `assertOrgWritable(ctx, what)`         | `readOnly` context → FORBIDDEN 403 with `details.reason = "read_only_support_access"` and the grant id. `requireOrgContext(permission)` applies it to every permission that is not a `*.read` before the RBAC check                                                                                                                                                                                                                                                                                                                                                                          |
| 4. RBAC               | `assertCan(role, permission)`          | FORBIDDEN without the permission                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| route handlers        | `requireApiOrgContext({ signedOut? })` | same gate, answers instead of redirecting: 401 `UNAUTHORIZED`, 403 `FORBIDDEN` + `reason: "organization_suspended"` (used by every `/api/app`, `/api/ai`, `/api/privacy`, OAuth route)                                                                                                                                                                                                                                                                                                                                                                                                       |
| database              | `withOrg(ctx, …)`                      | a support session runs every tenant transaction with `SET LOCAL transaction_read_only = on` (SQLSTATE 25006 on any write), so a mutation that slips past the application guard still fails                                                                                                                                                                                                                                                                                                                                                                                                   |

Mutations that are guarded by a `*.read` permission or by none call `assertOrgWritable` explicitly before their first write: `updateAiMotionAction` (`org.read`; the preference row lives inside the tenant), `decideApprovalRequestAction` and `withdrawApprovalRequestAction` (`members.read`). `updateLocaleAction` changes only the operator's own language cookie in a support session, never the organisation's setting; `setActiveSiteAction` (`sites.read`) validates the site and switches through the `ts-active-site` cookie alone (no preference row, no audit row of its own — the page view is audited with the grant id; the environment stays the site's default). The Track AI routes (`/api/ai/chat|confirm|wizard`) refuse a support session with `code: FORBIDDEN, reason: "read_only_support_access"`. Every other mutating server action passes a write permission to `requireOrgContext` (`grep '"use server"'` → `requireOrgContext("<x>.manage|update|create|invite|remove|verify|dsar|retention")`), so the guard is central; `apps/web/src/server/session.test.ts` covers the suspension error, the API answers, the read-only refusal per permission and `assertOrgWritable`.

### Customer dashboard entry points

- **Banner slot** (`components/app/shell/app-shell.tsx`): `SupportAccessBanner` (operator: "support access active until … (grant …)" with the way back to `/ops/break-glass` and "leave support view"; the organisation's members: "read-only support access is active" with the link to `/app/team/audit`) renders **together with** `AnnouncementsBanner` (platform announcements from Controls, dismissible per browser). ### Client bundles

### Module rules fixed by the slices (summary; details in the module sections)

- **Organisations**: events column = accepted events of the last 30 days from `event_aggregates`; last activity = newest aggregate bucket or audit entry within 90 days (null shown as "none in 90 days"); health = rounded average of the latest `site_health_snapshots` row per active site ("not measured" without snapshots), tones as in the Command Center (≥ 80 ok, ≥ 50 warn); snippet state verified / pending / none; destination snapshots stale after 5 minutes. Suspend / unsuspend and feature-flag overrides are `PLATFORM_ADMIN`, notes `PLATFORM_SUPPORT`; the CSV export (`/ops/organisations/export`) is audited as `platform.organizations.export` and capped at 5000 rows (`X-Export-Truncated`). The detail page's tab title carries the id prefix (no second round trip before render).
- **Break-glass**: the customer's audit log shows the operator as "Track support" (`AuditActorView.kind = "platform"`, grant id, never the operator's e-mail or name). Leaving the support view clears the cookie and audits `ops.break_glass.close`; the grant stays active until revoked or expired.
- **Platform health**: `WORKER_JOB_INTERVALS_MS` mirrors `JOB_SCHEDULE` of the worker (apps must not import each other) — a new worker job must be added there to get staleness detection; the audit-failure list filters `audit_log` on `action LIKE '%fail%' OR '%error%'` over 7 days (limit 20); the collector probe runs inside the render with a 4 s timeout; times in UTC; page auto-refresh every 60 s.
- **Revenue**: MRR/ARR are catalogue list prices (yearly ÷ 12) without Stripe discounts, taxes or proration; rows with interval null, unknown plan ids or Enterprise are "not priced"; trials never count; cancellation windows use Stripe's `canceled_at`; overage exposure applies the organisation's policy like the usage guard and is labelled "not an invoice"; a 403 from the restricted Stripe key is shown honestly; page views are not audited, CSV exports are (`platform.revenue.export`).
- **Controls**: suspension is enforced in the customer API through `requireApiOrgContext` (JSON 403, OAuth start/callback included); `getOrgContext()` still hands out a suspended organisation to the dashboard layout so the notice can render.
- **Inbox**: audit entries carry `organization_id = null` (public-form data), the requester's organisation as `metadata.linkedOrganizationId`; a sent reply moves a `new` request to `in_progress` and assigns it when unassigned; mark-as-spam and replies need a confirmation; the detail page shows the requester's business contact data, never `ip_hash` / `ua_family`.
- **Growth**: sign-ups count every `user` and `organization` row (operators and suspended organisations included, stated as "all accounts"); "destination connected" and "paying" are proxies (creation date of a currently connected integration / of an active subscription row); retention rests on `event_aggregates` with accepted > 0 (horizon shown); no geographic split (no country column exists).
- **Audit**: metadata only (redacted diffs), so page views need no grant and are not audited; CSV exports are (`platform.audit.export`, with the tenant's `organization_id` when scoped); the break-glass scope matches `ops.break_glass.*` / `platform.break_glass.*` actions and `metadata.breakGlassId`; offset pagination up to page 10 000.
- **Platform users**: with exactly two eligible admins neither can change the other's role in the console (`needsThirdAdmin`) — grant a third admin first or use `ops:grant`; the single-admin fallback (ticket + reason, self-approved) applies only when no other eligible admin exists.
- **Content**: read-only, no tenant data, no audit rows (§9).
- **Support** (docs/18): every ticket mutation is an audited server action with the SLA engine as the one clock model (persisted clock run since 0018); inbound mail is untrusted (authenticated senders only for organisation links and reply threading, a structural replay guard, a reprocess of failed deliveries for admins); sending claims the message row atomically; the sub-pages (Tickets, Views, Macros, Reports, Settings) share a secondary navigation on every `/ops/support` page and the "Support" entry of `OPS_NAV` carries the live queue badge (docs/18 §18).

### Open follow-ups

- Dashboard error boundary (`app/app/error.tsx`) shows the suspension notice through `error.digest`; a dedicated notice page keyed on `details.reason === "organization_suspended"` would be cleaner.
- `audit_log` has no `(created_at desc, id desc)` index and no expression index on `actor->>'kind'`: the unfiltered audit explorer and the platform-only filter scan on a large log (migration 0015 candidate).
- `event_aggregates` has no index on `bucket_start` (growth horizon / activity queries).
- Two-factor self-service enrolment exists on `/app/settings/security` (§3 "Enrolment"); the seeded `ops@acme.test` still has no enrolment, so the local console keeps `OPS_REQUIRE_2FA=false` and `ops.spec.ts` keeps needing it.
- The support session switches sites through the cookie only; a per-environment switch for operators would need a cookie for the environment as well.
- The e2e flows leave one feature flag per run in the dev database (`e2e.smoke_<stamp>`; flags cannot be deleted) and a revoked announcement row; a delete action for unused, manual flags would let the spec clean up after itself.
- Success notices of the other console modules (Controls, Organisations, Inbox, Users) live next to their tables and survive because the row stays; the break-glass pattern (`notice.tsx`) is the model should a row-moving action be added elsewhere.
